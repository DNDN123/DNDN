01 왜 합치는가

두 트리가 상호 보완적이었습니다. 통합본은 발표·정량평가·회귀가 강했고, "LLM for OS"는 자연어 셸·온디바이스 모델·정리 도구가 앞서 있었습니다. 앞선 부분을 통합본으로 끌어와 하나의 완성본으로 만듭니다.

기존 integration/ 강점

  • 4팀 슬라이스 단일 트리 (빌드·부팅 PASS)
  • 3-way 정량 평가 + 차트
  • sanity_check.sh 8/8 회귀
  • KO/EN 리포트·슬라이드

"LLM for OS"에서 가져온 앞선 부분

  • 라이브 인콘솔 NL 셸 (ask → 자동 실행)
  • 온디바이스 백엔드 (solar / local / offline)
  • executor + agent (SafetyGuard · 추상요청 분해)
  • reap syscall + 유저 도구 7종

원천 haneol는 보호 대상 원본 브랜치 — 읽기만 하고 추가·수정은 전부 integration/ 에만 적용 (원본 보호 원칙 유지).

02 · ARCHITECTURE

03 라이브 NL 셸 흐름

xv6 콘솔 안에서 자연어를 말하면, 호스트 브리지가 번역·가드 후 같은 콘솔에 명령을 자동 주입합니다.

xv6 콘솔: ask 7번 꺼줘→ @@NL 센티넬→ nlbridge 포착→ executor.classify (LLM)→ SafetyGuard→ 콘솔 자동주입 → kill 7

LLM은 커널에 들어가지 않는다

모델은 호스트에서 자연어 → intent JSON 만 생성. 커널엔 번역된 작은 명령(예 kill 7)만, 즉 syscall 경계를 넘습니다. 큐 힌트는 {0,1,2} 2-bit로 축약.

호스트↔게스트 콘솔 왕복 = IPC

두 프로세스(QEMU 게스트 · 브리지) 사이 콘솔 라운드트립 자체가 IPC 채널 — 프로세스·스케줄링·동기화에 더해 OS 개념 하나 추가.

04 · EXECUTOR + SAFETY

05 intent 실행기 + 안전가드 (M3)

자연어 → spec → xv6 명령. 실행 전 마지막 방어선이 SafetyGuard.

build_command — 20 인텐트 매핑

  • 워크로드 cpu/io/mixed_burner → nlrun <q> … &
  • 프로세스 kill·setpri·trace·ps
  • 정리 killall·killheavy·reap
  • 시스템 uptime·sysinfo

SafetyGuard — 3-verdict

  • reject pid 0·1 보호, 범위 밖, 주입
  • confirm 파괴적(kill·rm·killall·killheavy)
  • allow 안전한 조회·실행

python executor.py --selftest → 14종 verdict 통과 · python test_nlos.py → ALL CHECKS PASSED (모델·QEMU 불필요, 어느 머신에서나).

06 · KERNEL

07 신규 syscall — reap (36)

유저 도구 7개 중 reap만 새 syscall 필요 — 나머지는 기존 ps/getstats/settrace/kill/uptime/sysinfo 재사용.

proc_reap_zombies() — 안전한 정리

버려진 ZOMBIE(부모가 init이 아닌)를 init으로 reparent + init 깨우기. freeproc()를 직접 부르지 않고 init의 wait() 검증된 경로로 해제. 락 순서 wait_lock → p->lock (reparent와 동일).

8개 파일 일관 와이어링

  • syscall.h #define SYS_reap 36
  • syscall.c extern + 디스패치 배열
  • sysproc.c sys_reap()
  • proc.c 본체 · defs.h 선언
  • usys.pl · user.h · Makefile

정적 검증: 와이어링 grep 일치 · perl usys.pl가 reap 스텁 생성 · 구조체 정합(procinfo/procstats/sysinfo, ZOMBIE=5) 확인.

LLM FOR OS — IDENTITY

09 "thin wrapper"가 아닌 이유

강의계획서 한 줄 — "Thin wrappers around an LLM API … will not be accepted." — 을 정면으로 통과.

원칙 1 커널은 LLM을 모른다

모델 출력은 syscall 경계에서 작은 정수/명령으로 축약. 잘못된 큐 값은 syscall이 거부.

원칙 2 OS가 자가 교정

CPU-bound가 HIGH로 잘못 배치돼도 MLFQ demotion이 몇 tick 안에 LOW로 강등 — LLM은 초기 힌트만.

원칙 3 LLM 없이도 동작

키·네트워크 없으면 offline 규칙 폴백 — 데모가 안 깨짐. 온디바이스면 클라우드도 불필요.

실제 구현은 xv6 3-단계 MLFQ · 다수 syscall · 안전가드 · 호스트 브리지 — 진짜 OS 작업. 온디바이스 파인튜닝 모델은 "thin wrapper"와 정반대.
