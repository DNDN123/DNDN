> B로 결정한 팀이 *어떤 B 주제*로 갈지 정하기 위한 자료.

## 0. B 주제 선정의 핵심 기준

강의계획서의 *"thin wrapper 금지"* 조항을 절대 통과해야 하므로, 모든 후보를 다음 4가지 기준으로 평가:

| 기준 | 의미 | 가중치 |
|---|---|---|
| **OS 본질 충족도** | 우리가 *직접 구현*하는 OS 메커니즘이 있는가? LLM 빠져도 시스템이 동작하는가? | ⭐⭐⭐⭐⭐ |
| **약한 팀 구현 가능성** | Python으로 구현 가능? 시스템 코드(C/커널) 없이 가능? | ⭐⭐⭐⭐⭐ |
| **평가 지표 객관성** | LLM 응답 품질이 아니라 *OS 메커니즘 성능* 으로 평가 가능? | ⭐⭐⭐⭐ |
| **차별화** | 다른 팀이 흔히 시도하는 것과 다른가? | ⭐⭐⭐ |

> 가장 무서운 함정: *"LLM 응답이 좋은가"* 가 평가 대상이 되는 주제. 우리 통제 밖이고 강의 평가 기준에도 안 맞음.

## 2. 후보별 상세

### B-α: 페이지 교체 힌트 오라클 ⭐ **1순위 추천**

**한 줄 설명**: 우리가 만든 페이지 교체 시뮬레이터(LRU/Clock/FIFO)에 LLM이 워크로드 패턴을 보고 *"다음에 어떤 페이지가 곧 접근될지"* 힌트를 제공.

**시스템 구조**
```
[워크로드 트레이스]
        ↓
  [트레이스 일부] → [LLM 힌트 제공자] → [예측: 다음 접근 예상]
        ↓                                         ↓
  [페이지 교체 시뮬레이터] ←───────── [힌트 받아 교체 결정 보정]
        ↓
  [Page Fault Rate]
```

**OS 본질**: LRU/Clock/FIFO 알고리즘 직접 구현. LLM 빠져도 시뮬레이터 단독 동작.

**활용 강의 내용**
- Week 11: paging, page table 개념
- Week 12: ⭐ **LRU/Clock/FIFO/Belady's Anomaly** (그대로 코드)
- Week 7: 알고리즘 평가 방법론

**평가 지표**
- 기본 LRU vs *LRU + LLM 힌트* 의 page fault rate 차이
- 워크로드 종류별(시퀀셜/랜덤/locality 강함) 성능 비교
- LLM 힌트 정확도 측정

**4인 분담**
- ① 시뮬레이터 코어 (FIFO/LRU/Clock) — Python, ~300줄
- ② LLM 힌트 모듈 (프롬프트 + Solar API)
- ③ 워크로드 생성기 (시퀀셜/랜덤/loop/Zipf 분포)
- ④ 평가·시각화 (matplotlib 차트, 보고서)

**예상 데모**: *"같은 워크로드를 LRU vs LRU+힌트로 돌렸을 때 page fault가 23% 줄어들었습니다"* 차트 한 장으로 명확.

**리스크**
- LLM이 의미 있는 힌트를 못 줄 수 있음 → 그것 자체도 흥미로운 결과 (negative result로 보고서)
- 워크로드를 너무 단순하게 만들면 차이가 안 보임 → Zipf 분포 등 *현실적* 워크로드 필요

**예상 노력**: 1인당 35~45시간 (디버깅 버퍼 포함)

### B-β: 데드락 가설 도우미

**한 줄 설명**: 멀티스레드 프로그램의 락 의존성 그래프를 LLM이 분석해 *"어떤 락 순서로 데드락이 발생할 수 있는지"* 가설 제시.

**시스템 구조**
```
[샘플 멀티스레드 프로그램들]
        ↓
[락 그래프 추출기 (정적 분석)] → [Resource Allocation Graph]
        ↓
[LLM 가설 제시] ↔ [실제 실행으로 검증]
        ↓
[데드락 발생 시나리오 + 수정 제안]
```

**OS 본질**: 락 그래프 자료구조 직접 구현 + 사이클 검출 알고리즘 (Banker's, Detection).

**활용 강의 내용**
- Week 4: mutex, spinlock
- Week 9: 동기화
- Week 10: ⭐ **데드락 4 조건, RAG, Banker's Algorithm** (그대로)

**평가 지표**
- 기본 사이클 검출 알고리즘 vs *LLM 가설 우선순위 적용* 의 검출 시간/정확도

**리스크**: 락 그래프 추출이 의외로 어려울 수 있음 (정적 분석 vs 동적 트레이싱). 시간 소진 위험.

**차별화**: ★★★★★ (이 주제로 하는 팀 거의 없음)

---

### B-γ: 스마트 프리페처 (캐시 힌트)

**한 줄 설명**: 파일/페이지 접근 패턴을 보고 LLM이 *"다음에 어떤 파일·페이지를 미리 메모리로 로드해두면 좋을지"* 힌트.

**OS 본질**: 캐시 자료구조 직접 구현 + LRU 변형 + prefetch 정책.

**활용 강의 내용**
- Week 11-12: paging, demand paging
- Week 13: 파일시스템

**B-α과 비교**
- B-α: *"교체 결정"* 에 LLM 힌트
- B-γ: *"prefetch (미리 가져옴)"* 에 LLM 힌트
- 본질적으로 비슷하지만 B-γ는 prefetch라는 *추가 메커니즘*을 구현해야 해서 약간 더 복잡

**리스크**: B-α보다 살짝 어려움. 약한 팀에는 B-α가 더 안전.

---

### B-δ: 자연어 셸 + 안전 샌드박스

**한 줄 설명**: 사용자가 *"이 폴더에서 PDF 파일만 다른 폴더로 옮겨줘"* 라고 자연어 입력 → LLM이 명령 변환 → 안전 샌드박스가 검증 후 실행.

**OS 본질**: 안전 샌드박스 (권한 격리, 화이트리스트, 미리보기) — 직접 구현. LLM 부분은 thin이지만 샌드박스가 OS 컴포넌트.

**약점**
- *thin wrapper* 함정 위험 큼 (샌드박스를 정성껏 만들지 않으면)
- 다른 팀 흔한 주제 (차별화 약함)
- 평가가 *"명령 변환 정확도"* 가 되기 쉬움 → LLM 품질 의존

**리스크가 큰 이유**: OS 본질이 *샌드박스*에만 있는데, 샌드박스를 *진지하게* 만들려면 권한 모델·격리·검증 등 일이 많음. 약한 팀에 부담.

---

### B-ε: 로그 분석 / 진단 도우미

**한 줄 설명**: dmesg, journalctl 로그를 LLM이 읽고 시스템 문제를 진단·요약.

**약점**
- ⚠️ **Thin wrapper 위험 가장 큼** — *"로그 텍스트 → LLM → 요약"* 구조가 거의 그대로면 평가 탈락
- 다른 팀들이 가장 자주 시도하는 주제 (차별화 0)
- OS 컴포넌트가 약함

**언제 가능한가**: 의식적으로 *로그 인덱싱 자료구조*나 *시스템 콜 트레이서*를 직접 구현하면 가능. 그런데 그러면 난이도가 올라가서 약한 팀에 부담.

> 약한 팀이 학기 마지막 발표에서 *"우리 OS 컴포넌트는...?"* 으로 곤란해질 가능성이 가장 큰 주제. **권장하지 않음.**

### B-ζ: 스마트 OOM 킬러 ⭐ **2순위 추천**

**한 줄 설명**: 메모리 부족 시 어떤 프로세스를 종료할지 LLM이 *"이 프로세스의 중요도, 메모리 사용 패턴, 사용자 기대"* 를 보고 추천. 우리는 OOM 시뮬레이터를 직접 구현.

**시스템 구조**
```
[프로세스 시뮬레이터]
- PID, 메모리 사용량, CPU 사용률, 우선순위, 부모 PID, 실행 시간
        ↓
[메모리 압력 시뮬레이터] → 메모리 한계치 도달
        ↓
[기본 OOM 정책 (oom_score)] vs [LLM 정책 (컨텍스트 인지)]
        ↓
[프로세스 선택 및 종료 시뮬레이션]
        ↓
[평가: 시스템 안정성, 중요 프로세스 보존율]
```

**OS 본질**: 프로세스 시뮬레이터 + 메모리 압력 모델 + OOM 점수 계산 직접 구현.

**활용 강의 내용**
- Week 2: 프로세스, PCB
- Week 11-12: 메모리 관리
- Week 6-7: 우선순위·중요도 (스케줄링과 유사 개념)

**평가 지표**
- 기본 oom_score vs LLM 추천의 *"중요 프로세스 보존율"*
- 시스템 안정 회복 시간
- "사용자 만족도" (시뮬레이션된 시나리오 기준)

**4인 분담**
- ① 프로세스/메모리 시뮬레이터 — Python (PCB-like 클래스, 메모리 할당 시뮬레이션)
- ② LLM 정책 결정 모듈 (각 프로세스 정보 → 종료 우선순위)
- ③ 시나리오 생성기 (메모리 폭주 워크로드: fork bomb, 메모리 누수, 정상 부하)
- ④ 평가·시각화 + 비교 분석

**예상 데모**: *"동일 메모리 압력 상황에서 기본 OOM이 중요 DB 프로세스를 죽인 반면, LLM 정책은 백그라운드 마이너 프로세스를 죽여 시스템이 정상 복구됨"*

**차별화**: ★★★★ (이 변형도 흔하지 않음)

**리스크**: 시나리오 설계가 까다로움. *"중요한 프로세스"* 의 정의를 잘 짜야 평가가 의미 있음.

**예상 노력**: 1인당 40~50시간

### B-η: 시스템 콜 트레이스 분석기

**한 줄 설명**: `strace` 출력을 LLM이 분석해 *"이 프로그램이 무엇을 하는지, 비정상 행동이 있는지"* 설명.

**약점**: 본질이 *"strace 출력 → LLM"* 이라 thin wrapper 가깝다. 의식적으로 시스템 콜 인덱싱이나 패턴 매칭 엔진을 직접 만들지 않으면 평가 위험.

**B-ε과 비슷한 위험**: 추천하지 않음.

---

### B-θ: 스케줄러 우선순위 추천기

**한 줄 설명**: 실행 중인 프로세스들의 패턴을 보고 LLM이 *"이 프로세스에는 이 우선순위가 적합"* 추천. 우리는 MLFQ 시뮬레이터 직접 구현.

**시스템 구조**
```
[프로세스 워크로드 트레이스]
        ↓
[MLFQ 시뮬레이터 (기본)] vs [MLFQ + LLM 우선순위 추천]
        ↓
[평가: turnaround time, response time, fairness]
```

**OS 본질**: ⭐ **MLFQ 직접 구현** — Week 7에서 배운 그대로.

**활용 강의 내용**
- Week 6-7: ⭐ **FCFS/SJF/Priority/RR/MLFQ** (그대로 코드)

**평가 지표**: turnaround / response time / fairness — 강의에서 배운 척도 그대로

**4인 분담**
- ① MLFQ 시뮬레이터 (3-level queue, aging, time slice)
- ② LLM 우선순위 추천 (프로세스 특성 → 큐 레벨 추천)
- ③ 워크로드 생성기 (CPU-bound, I/O-bound, mixed)
- ④ 평가·시각화 (간트차트, 메트릭)

**B-α과의 차이**
- B-α: *메모리* 영역 (page replacement)
- B-θ: *CPU* 영역 (scheduling)
- 둘 다 강력하지만, B-α는 Week 12 진도와 정확히 맞물리고, B-θ는 Week 6-7 (이미 배운) 진도 활용

**선택 팁**: 팀이 *이미 배운 내용*에 더 자신 있으면 B-θ, *앞으로 배울 내용을 활용*하고 싶으면 B-α.

**예상 노력**: 1인당 35~45시간

## 4. 최종 추천 — **B-α (페이지 교체 힌트 오라클)** 입니다

### 이유

**1. 강의 진도 활용도가 최고**
Week 11(paging)과 Week 12(LRU/Clock/FIFO/Belady) 진도가 *그대로 코드*가 됩니다. 약한 팀일수록 *"수업 노트 = 사양서"* 의 가치가 절대적이에요. 다른 후보들은 강의 진도 활용도가 부분적입니다.

**2. 평가 지표가 가장 객관적**
*"page fault rate가 23% 줄었다"* — 차트 한 장으로 끝납니다. 주관적 판단 들어갈 여지가 없어요. B-ζ는 *"중요한 프로세스의 정의"* 같은 주관적 요소가 들어가고, B-θ는 평가 지표는 명확하지만 LLM의 기여를 분리하기 살짝 더 까다로워요.

**3. 구현 분량이 가장 작음**
시뮬레이터 코어가 약 300줄. B-ζ(~500줄), B-θ(~400줄)보다 작아요. 약한 팀이 6주에 끝낼 수 있는 안전한 분량.

**4. 실패해도 흥미로운 결과**
LLM이 의미 있는 힌트를 못 주면 *그것 자체*가 *"LLM은 이런 종류의 시스템 결정에 적합하지 않다"* 는 흥미로운 negative result. 보고서에 정직하게 쓰면 평가에 도움.

**5. Thin wrapper 함정 자동 회피**
시뮬레이터 자체가 OS 알고리즘 구현이므로 LLM이 빠져도 발표할 게 있습니다. 약한 팀의 안전망.

## 5. 만약 B-α가 끌리지 않는다면

팀의 관심사·강점에 따라:

- **시스템 시나리오 분석에 흥미** → **B-ζ (OOM 킬러)** 선택. 좀 더 *현실적인 시스템 문제*를 다루는 느낌.
- **이미 배운 스케줄링이 더 익숙** → **B-θ (스케줄러 추천기)** 선택. Week 6-7 자산 직접 활용.
- **데드락에 흥미** → **B-β (데드락 가설)** 선택. 차별화 최강이지만 락 그래프 추출 난이도가 변수.

다른 후보(B-δ, B-ε, B-η)는 약한 팀에 권장하지 않습니다 (thin wrapper 위험 또는 OS 본질 약함).

## 7. 마지막 한 마디

B 방향에서 *"thin wrapper 함정"* 을 피하는 가장 안전한 길은 ***"우리가 직접 구현한 OS 알고리즘 시뮬레이터 위에 LLM이 힌트만 얹는다"*** 구조예요. B-α, B-γ, B-θ 모두 이 패턴을 따르고, 그래서 평가 통과 확률이 높습니다.

LLM이 *대체*하는 게 아니라 *향상*하는 역할이고, 우리가 만든 OS 알고리즘이 *주인공* 인 구조 — 이게 강의계획서가 원하는 바로 그 모양입니다.
