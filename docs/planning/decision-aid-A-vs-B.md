# Direction A vs B — 솔직한 비교 + 결정 가이드

> 한쪽 편을 들지 않고, 팀이 스스로 결정할 수 있도록 정리한 문서.

---

## 1. 솔직한 장단점 비교

### Direction A — OS for LLM (에이전트 미니 OS)

**장점**

- **OS 개념이 시스템의 본질** — *"OS 개념을 어디 썼나"* 질문에 자동으로 답이 됨. 강의계획서의 *thin wrapper 금지* 조항을 정면 통과.
- **Week 1–7 학습 자산을 직접 활용** — 스레드 풀, 유저레벨 스레드 라이브러리, xv6 스케줄러 분석 등이 그대로 부품이 됨.
- **앞으로 배울 내용(Week 9–13)이 다음 모듈과 일치** — 강의 진도와 빌드 일정이 자연스럽게 맞물림.
- **차별화** — 다른 팀들이 B에 몰리면 자동으로 눈에 띔. Peer review에서 유리할 수 있음.
- **시스템 프로그래밍 깊이** — OS 수업의 핵심을 진짜로 손으로 만들어보는 경험.

**단점**

- **시스템 코드 디버깅이 어려움** — race condition, deadlock은 재현조차 힘듦. 한 번 막히면 며칠 단위로 시간이 녹음.
- **모듈 간 커플링이 큼** — 한 사람이 못 따라오면 전체에 영향. 협업 부담 큼.
- **데모 임팩트가 약할 수 있음** — *"백그라운드에서 잘 돌아간다"* 는 시스템은 시각화를 잘 안 하면 발표에서 임팩트가 약함.
- **LLM 노출이 적음** — 이 프로젝트로 LLM/프롬프트 엔지니어링 경험을 쌓고 싶다면 A는 그쪽 비중이 작음.
- **OS 외 분야 포트폴리오 가치는 제한적** — 시스템/커널 직군 외에는 *"이거 뭐예요?"* 로 끝날 수 있음.
- **과도한 엔지니어링 위험** — 학기 프로젝트 스케일을 넘어서 무리한 설계로 가기 쉬움.

---

### Direction B — LLM for OS (NL 셸, 진단 도우미 등)

**장점**

- **첫 주에 뭐라도 돌아가는 결과물** — LLM API 호출만 붙여도 데모 가능. 심리적 안전감 큼.
- **LLM/프롬프트 엔지니어링 실전 경험** — 요즘 산업에서 가장 가치 있는 스킬을 직접 키움.
- **데모가 화려함** — 자연어 입력 → 시스템 동작이 누구에게 보여줘도 직관적.
- **포트폴리오로 활용성 높음** — 비-OS 직군(웹/AI/풀스택)에 면접 어필이 쉬움.
- **모듈 독립성** — 프론트/백엔드/프롬프트/평가가 비교적 독립적으로 굴러감. 한 명이 막혀도 다른 영역 진행 가능.
- **창의적 자유도** — *"어떤 OS 문제에 LLM을 붙일까?"* 라는 질문 자체가 열려 있어서 아이디어 다양화 가능.
- **사용자가 있는 도구** — 다른 학생들이 실제로 써볼 수 있는 결과물이 나올 수 있음.

**단점**

- **Thin wrapper 함정** — 강의계획서가 명시적으로 경고한 *"OS 각도가 약한 LLM 래퍼"* 가 되기 쉬움. 의식적으로 OS 개념을 끼워 넣어야 함.
- **OS 수업으로서의 정체성이 약함** — 발표에서 *"우리 프로젝트의 OS 컴포넌트는 무엇인가"* 에 답하기 어려울 수 있음.
- **Week 1–7 학습 자산을 거의 안 씀** — 스레드 풀, MLFQ, 병렬 해시테이블 같은 핵심 자산이 거의 등장하지 않음.
- **OS 개념을 "본질적으로" 넣으려면 결국 어려워짐** — 예: LLM이 페이지 교체 힌트를 주는 구조 → 결국 페이지 교체 알고리즘을 직접 구현해야 함.
- **LLM 품질 의존성** — Solar API가 잘못된 답을 주면 데모 자체가 무너짐. 우리가 통제 못 하는 변수.
- **평가가 LLM 응답 품질에 좌우될 수 있음** — *"우리 시스템이 좋은가"* 와 *"LLM이 좋은가"* 가 분리되지 않음.

## 2. A가 더 나은 케이스 vs B가 더 나은 케이스

| 상황 | 더 나은 선택 |
|---|---|
| 팀 전원이 시스템 프로그래밍에 어느 정도 익숙함 | **A** |
| 팀에 시스템 코드가 처음인 사람이 1명 이상 있음 | **B** |
| OS 수업 학점을 최우선시 | **A** |
| 이 프로젝트로 포트폴리오/취업 어필을 원함 | 케이스 바이 케이스 (A는 시스템 직군, B는 일반 SWE) |
| 팀이 빠르게 동기부여 받는 게 중요 (성취감) | **B** (초기 데모가 빨리 나옴) |
| 차별화/발표 임팩트 중요 | **A** (B팀이 많을수록 더 유리) |
| LLM 자체에 관심이 큼 | **B** |
| OS 자체에 관심이 큼 | **A** |
| 4명이 6주간 빡세게 갈 의지 있음 | **A** |
| 6주간 적당한 페이스를 원함 | **B** |
| 팀 내 협업 비용을 최소화하고 싶음 | **B** (모듈 독립성 큼) |
| 강의계획서의 *thin wrapper* 조항을 가장 두려워함 | **A** (자동으로 통과) |

## 3. 결정 프레임워크 — 5분 안에 정해보기

### Step 1: 팀원 각자 답하기 (1분)

다음 5문항에 **A 또는 B로** 답하세요:

1. 이 프로젝트로 **무엇을 가장 배우고 싶은가**?
   - 시스템 프로그래밍 / OS 메커니즘 → **A**
   - LLM / 프롬프트 / AI 통합 → **B**

2. **막혔을 때 가장 두려운 시나리오**는?
   - 시스템이 race condition 으로 무너지는 것 → **B** (회피)
   - 발표에서 *"OS 개념이 어디 있나"* 질문에 답 못 하는 것 → **A** (회피)

3. **팀 협업 스타일**은?
   - 모두 같은 코드베이스에 깊이 들어가서 함께 디버깅 → **A**
   - 각자 영역을 맡아 독립적으로 진행 → **B**

4. **6주 후 발표에서 보여주고 싶은 그림**은?
   - 동시에 돌아가는 에이전트들의 프로세스 테이블 + 메모리 맵 시각화 → **A**
   - 자연어로 명령하면 OS가 알아서 동작하는 라이브 시연 → **B**

5. **포트폴리오 가치**로 보면?
   - 시스템/커널/인프라 직군 지원 → **A**
   - 일반 SWE / AI / 스타트업 지원 → **B**

### Step 2: 합산

- A가 4–5개: 망설이지 말고 **A**
- B가 4–5개: **B로 가되, OS 개념을 본질적으로 넣을 설계를 먼저 잡고 시작**
- 3:2 또는 2:3: 다음 단계로

### Step 3: 결정적 질문 두 개 (3:2 인 경우)

**질문 1:** *"이 프로젝트는 OS 수업 평가용인가, 우리 학습/포트폴리오용인가?"*
- OS 수업 평가가 우선 → **A**
- 학습/포트폴리오가 우선 → **B**

**질문 2:** *"6주 후, 우리가 강의계획서의 'thin wrapper 금지' 조항에 자신 있게 답할 수 있는 설계를 지금 그릴 수 있나?"*
- 자신 없음 → **A** (이 위험을 피함)
- 자신 있음 → **B** 가능 (단, 그 설계를 첫 주에 명확히 문서화)

## 4. B를 선택할 경우의 안전 가이드

만약 팀이 B로 기울었다면, 아래 조건을 모두 만족하는 형태로 설계하세요. 이것 없이는 *thin wrapper* 함정에 빠집니다.

- ✅ **OS 메커니즘을 직접 구현하는 부분이 있다.** (예: 페이지 교체 시뮬레이터, 스케줄러, 로그 인덱싱 자료구조 등)
- ✅ **LLM이 빠져도 시스템이 동작한다.** (LLM은 *향상* 시키는 역할이지, *대체* 하지 않음)
- ✅ **평가 지표가 LLM 응답 품질이 아니라 OS 메커니즘 성능에 있다.** (예: hit rate, throughput, fairness)
- ✅ **블록 다이어그램에서 OS 컴포넌트가 박스 면적의 50% 이상이다.**

이 조건을 만족하는 B 변형 추천:

> **"LLM이 워크로드 패턴을 보고 페이지 교체에 힌트를 주는 시스템"**
> — 우리는 LRU/Clock/FIFO 페이지 교체 시뮬레이터를 직접 만들고, LLM은 *"이 워크로드는 곧 시퀀셜 스캔이 올 것 같다"* 같은 힌트만 제공. 평가 지표: 힌트 있을 때 vs 없을 때의 page fault rate.

이 형태는 OS 본질을 잃지 않으면서 LLM도 핵심 역할로 들어옵니다.

## 5. A를 선택할 경우의 안전 가이드

만약 팀이 A로 기울었다면, 아래 조건으로 *"망할 위험"* 을 줄이세요.

- ✅ **Week 11까지 무조건 end-to-end 뼈대 완성** — 스케줄러 1종, 메모리 1종, 도구 1개. 일단 *"에이전트 2개가 동시에 파일 읽는다"* 만 되면 OK.
- ✅ **각 모듈이 독립 데모 가능** — 한 모듈 망가져도 발표 자료가 비지 않음.
- ✅ **모니터링 대시보드 필수** — 시스템이 잘 돌아도 시각화 없으면 임팩트 약함. 프로세스 테이블, 메모리 맵, 큐 상태를 라이브로 보여주는 웹 UI 하나 필수.
- ✅ **폴백 영상 미리 녹화** — Week 13 dry-run 전에 라이브 시연 백업 GIF 확보.

## 6. 가장 정직한 한 마디

**둘 다 좋은 프로젝트가 될 수 있습니다.** A는 *"이 강의의 결정체"* 가 될 잠재력이 크고, B는 *"이 강의 + 산업 트렌드의 교차점"* 이 될 잠재력이 큽니다.

진짜 위험은 *어느 쪽을 골랐는가* 가 아니라 **고른 방향에 대해 팀 전체가 같은 그림을 갖고 있느냐** 입니다. 절반은 A를 그리고, 절반은 B를 그리고 있으면 6주 동안 합쳐지지 않아요.

그래서 이 문서를 같이 읽고, **§3의 5문항에 각자 답하고**, 결과를 공유한 다음, 그 자리에서 결정 내리시길 권합니다. 결정을 미루는 것이 가장 비싼 선택이에요.
