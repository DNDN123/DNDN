# Direction A 주차별 로드맵 — Solar-Agent OS (다운스케일 버전)

> 4인 / 6주 / 시스템 프로그래밍 경험 얕은 팀 기준.
> 무리하지 않으면서 강의계획서의 *"OS 개념 substantive 구현"* 을 충족하도록 스코프 조정.

---

## 0. 다운스케일 원칙

원래 계획에서 다음을 단순화합니다:

| 항목 | 풀 버전 | 다운스케일 버전 |
|---|---|---|
| 구현 언어 | C / xv6 | **Python (asyncio + threading)** |
| 동시 에이전트 수 | 무제한 | **최대 3개** |
| 스케줄러 | MLFQ | **라운드로빈 → (여유 시) 우선순위 큐** |
| 메모리 정책 | LRU + Clock + 압축 | **LRU 1개만** |
| 도구 샌드박스 | 풀 격리 | **파일 read 전용 + 화이트리스트** |
| IPC | 다중 채널 | **단일 메시지 큐** |
| LLM 모델 | Solar Pro 3 | Solar Pro 3 (변경 없음) |

이 정도가 약한 팀이 6주에 *완성*시킬 수 있는 한계선입니다.

---

## 역할 분담 (이 로드맵 기준)

- **A — 런타임 코어**: 프로세스 모델 + 스케줄러
- **B — 메모리 관리자**: 컨텍스트 가상화 + LRU eviction
- **C — 샌드박스 + 도구**: 파일 격리 + 도구 호출 인터페이스
- **D — 통합 + 평가 + UI**: IPC 메시지 큐 + 모니터링 대시보드 + 평가 지표

> 각 역할은 *"이 모듈이 망해도 본인 단독 데모가 가능"* 한 형태로 설계합니다.

## Week 10 — Problem statement + 시스템 스케치

**전체 목표**: 누가 봐도 이해되는 블록 다이어그램 + 모듈 인터페이스 정의.

**강의 진도 연결**: 데드락 (4 조건, prevention) → 락 순서·자원 할당 설계에 직접 적용

**팀 공통 작업**
- 시스템 블록 다이어그램 그리기 (draw.io 또는 손그림)
  - 박스 4개: Runtime Core / Memory Manager / Sandbox / Monitor
  - 화살표: 메시지 흐름, 락 보호 자원
- **모듈 간 인터페이스 합의** (가장 중요!)
  - "에이전트는 어떤 데이터 구조인가" 합의
  - "메모리 매니저는 무엇을 노출하는가" 합의
  - 이 합의가 깨지면 통합이 지옥이 됨

**개인 작업**
- **A**: `Agent` 클래스 설계 (PCB-like) — 상태 (READY/RUNNING/WAITING/DONE), 우선순위, 큐 위치
- **B**: 컨텍스트 윈도우 인터페이스 — `add_message(msg)`, `evict()`, `current_size()`
- **C**: 도구 호출 인터페이스 — `call_tool(name, args, agent_id)` + 화이트리스트 정책 파일
- **D**: 메시지 큐 인터페이스 — `send(from, to, msg)`, `recv(agent_id)` + 대시보드 와이어프레임

**주말까지 산출물**
- [ ] `docs/architecture.md` (블록 다이어그램 + 모듈 책임)
- [ ] `docs/interfaces.md` (모든 함수 시그니처)
- [ ] 각 모듈 빈 클래스(`pass`만 있는) 커밋
- [ ] CI 셋업 (lint + 빈 테스트 통과)

**리스크 / 대응**
- 인터페이스 합의 못 함 → 미팅 1시간 잡고 *"가장 작은 합의"* 부터 (예: Agent 구조체 필드만 먼저)
- 다이어그램이 추상적임 → 시연 시나리오 1개 ("에이전트 2개가 동시에 파일 1개 읽기")로 구체화

## Week 11 — 최소 동작 프로토타입 (가장 중요한 주)

**전체 목표**: ⚠️ **이번 주 끝에 end-to-end로 뭐라도 돌아간다.** 못 하면 12주에 절벽.

**강의 진도 연결**: paging, 페이지 테이블 → 컨텍스트 윈도우의 "가상 주소 공간" 비유 설계

**팀 공통 작업**
- 매일 15분 standup (월/수/금)
- 수요일에 통합 시도 — 잘 안 붙으면 다시 인터페이스 협의

**개인 작업** — 모두 *"가장 단순한 동작"* 만 구현
- **A**: 라운드로빈 스케줄러 + Agent 큐 — 에이전트 1개가 step 단위로 돌아감
- **B**: 컨텍스트 윈도우 (메시지 list) — *eviction 없이* 그냥 추가만 됨
- **C**: 단일 도구 (`read_file`) — 화이트리스트 디렉토리만 접근 가능
- **D**: Solar API 호출 워커 + 단일 에이전트 → API → 응답 받기

**주말까지 산출물 (이걸 못하면 비상)**
- [ ] **Hello World 시연**: 에이전트 1개가 *"파일 X를 읽고 요약해줘"* 라고 받으면 → 샌드박스가 파일 읽음 → LLM 호출 → 응답 출력
- [ ] 각 모듈에 단위 테스트 1개 이상
- [ ] `python main.py` 한 줄로 실행됨

**리스크 / 대응** ⚠️
- **이번 주 진도가 가장 위험**합니다. 못 끝내면 12주가 정체됨.
- **막히는 모듈은 즉시 페어 프로그래밍** — D가 끝나면 A·B·C 중 막힌 곳 도와주기
- 통합이 안 되면 → 인터페이스를 *"바보같이 단순한"* 것으로 후퇴 (예: 큐를 그냥 `list`로)

## Week 12 — 통합 + 평가 지표 정의

**전체 목표**: 동시에 *2~3개 에이전트*가 돌아가고, 측정할 수 있는 무언가가 있다.

**강의 진도 연결**: ⭐ **demand paging, LRU/Clock 페이지 교체** → 메모리 관리자에 직접 적용 (이번 주 진도 = 이번 주 코드)

**개인 작업**
- **A**: 라운드로빈 → 우선순위 큐 확장. 동시 2~3개 에이전트 안전하게 돌리기 (락 추가)
- **B**: ⭐ **LRU eviction 구현** — 컨텍스트 토큰 예산 초과 시 오래된 메시지 evict. (Week 12 강의 노트 그대로)
- **C**: 두 번째 도구 추가 (`list_dir` 또는 `write_file`) + violation 차단 테스트
- **D**: 모니터링 대시보드 v1 — 프로세스 테이블 (각 에이전트 상태 라이브 표시)

**주말까지 산출물**
- [ ] **Multi-agent 시연**: 에이전트 3개가 동시에 다른 파일을 읽고 LLM 호출 → 결과 출력
- [ ] **LRU 동작 시연**: 컨텍스트 가득 차면 가장 오래된 메시지가 evict 됨 (로그로 확인 가능)
- [ ] **평가 지표 1개 이상 정의 + 측정 가능**
  - 추천: *"LRU 적용 시 응답 정확도 vs 컨텍스트 토큰 사용량 트레이드오프"*
  - 또는: *"동시 에이전트 수에 따른 throughput"*

**리스크 / 대응**
- 동시성 버그 (race condition) 발생 → A가 추가한 락의 순서를 Week 10 데드락 강의 노트로 검증
- LRU 구현 어려움 → Week 11 강의 노트 + 강의 자료의 의사코드 그대로 옮김
- 통합 시점에 모듈 인터페이스 깨짐 → Week 10에 합의한 `docs/interfaces.md` 다시 보고 재정렬

## Week 13 — 평가 결과 + 발표 dry-run

**전체 목표**: 객관적 차트가 나오고, 발표 한 번 통째로 돌려본다.

**강의 진도 연결**: 파일시스템 (allocation, free space) → 샌드박스 FS 격리 강화에 활용

**개인 작업**
- **A**: 코드 리팩터링 + 코드 주석 보강 (보고서·발표용)
- **B**: 평가 실험 자동화 — 다양한 토큰 예산에서 LRU 성능 측정 + 차트 (matplotlib)
- **C**: Week 13 강의 내용으로 샌드박스 강화 (FS 권한 모델 적용) + violation 차단율 측정
- **D**: 라이브 데모 시나리오 + 백업 GIF 녹화 + 발표 슬라이드 초안

**팀 공통 작업**
- ⭐ **수요일 dry-run 1회**: 발표 시간 재면서 통째로 돌려보기
- 발표 후 피드백 → 슬라이드·시연 수정
- 보고서 초안 작성 분담 (각자 자기 모듈 섹션)

**주말까지 산출물**
- [ ] 평가 결과 차트 (최소 2장)
- [ ] 발표 슬라이드 초안 (영문)
- [ ] **데모 백업 영상 1개** (라이브 망칠 때 대비)
- [ ] 기술보고서 초안 (모듈별 1쪽씩)
- [ ] 개발 프로세스 문서 초안 (회의록·이슈로그)

**리스크 / 대응**
- 평가 결과가 *예상과 다름* → 그게 더 흥미로움. 솔직히 보고서에 쓰기
- 슬라이드 분량 못 맞춤 → 모듈당 1슬라이드로 압축

## 비상 대응 — Week 11 못 끝냈을 때

만약 Week 11 끝에 Hello World 가 안 되면, 즉시:

1. **스코프 추가 다운스케일** — 동시 에이전트를 1개로 줄이고 *"순차 처리 + 우선순위 큐"* 만 구현. 멀티에이전트는 stretch goal로 후퇴.
2. **모듈 통합 포기, 단독 모듈 방향** — 4명이 각자 *"단독으로 동작하는 작은 OS 컴포넌트"* 를 만들고, 발표는 *"각 모듈을 보여주는 형식"* 으로 전환. 임팩트는 줄지만 발표할 게는 있음.
3. **B로 피벗** — 가장 극단적 대안. Week 12 첫날까지가 마지노선. 그 이후는 늦음.

**1, 2번까지가 현실적 비상 대응이고, 3번은 정말 마지막 카드**입니다.
