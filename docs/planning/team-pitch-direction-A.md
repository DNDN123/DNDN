# 우리 팀, A로 갑시다 — Solar-Agent OS 제안

> 팀원들에게 보내는 제안서 — 5분이면 다 읽힙니다.

---

## TL;DR

- 다른 팀들이 B로 몰리는 이유는 **"망하지 않을까봐"** 입니다. 점수 기댓값이 아니라 점수 하한선을 지키려는 방어적 선택이에요.
- 그런데 우리가 7주 동안 손으로 만들어 온 것들 — 스레드 풀, 유저레벨 스레드 라이브러리, 병렬 해시테이블, xv6 스케줄러 분석 — 은 **거의 전부 A의 부품**입니다. B를 고르면 그게 다 사장돼요.
- 게다가 **앞으로 배울 Week 9~13 내용**(sleep/wakeup, 데드락, paging, page replacement, FS) **이 우리 프로젝트의 다음 모듈들과 1:1로 매칭**됩니다. 강의 진도가 곧 빌드 일정이에요.
- 즉, A는 *"새로 만드는 도전적인 프로젝트"* 가 아니라 **이 강의의 자연스러운 종착지**입니다.

---

## 1. 솔직히, B가 끌리는 거 압니다

자연어 셸이나 로그 진단 도우미 같은 B는 **첫 주에 뭐라도 돌아가는 걸 만들 수 있어요**. LLM API 호출 한 줄이면 시연 화면이 뜨니까요. 그래서 *"최악의 경우에도 발표할 게 있다"* 는 안전감이 있습니다.

이 안전감이 진짜라면 저도 B에 표를 던질 거예요. 그런데 **이 안전감은 학점 안전감이 아닙니다.**

## 2. B의 함정 — 강의계획서가 못박은 한 줄

> *"Thin wrappers around an LLM API — or projects where the OS angle is only 'it runs on Linux' — do not qualify and will not be accepted."*

이게 핵심이에요. B의 흔한 결과물 — *"LLM에게 dmesg 던지고 응답 받는 도구"*, *"자연어를 셸 명령어로 바꾸는 도우미"* — 은 이 문장에 정확히 걸립니다. **돌아가긴 하는데 평가가 안 되는 상태**가 가장 무서워요.

B로 살아남으려면 *"LLM이 힌트를 주고, 우리가 직접 만든 페이지 교체 알고리즘이 그걸 받아서 동작한다"* 같은 구조를 짜야 하는데, 그건 결국 **OS를 직접 구현해야 한다**는 뜻이고, 그러면 A만큼 어려워지는데 LLM은 부차적 역할이 돼서 매력도 사라집니다.

## 3. 우리가 이미 만든 것들을 봅시다

| 주차 | 우리가 손으로 짠 것 | A에서의 쓸모 |
|---|---|---|
| 02 | `fork/exec/pipe`, 미니쉘, 핑퐁 | 에이전트 = 프로세스 모델, IPC 파이프 |
| 04 | 병렬 해시테이블 (mutex/spinlock) | 공유 자원 동기화 — 그대로 사용 |
| 05 | **스레드 풀 직접 구현** | LLM API 호출 워커 풀 — **그대로 재활용** |
| 06 | **유저레벨 스레드 라이브러리 (12 테스트 통과)** | **이게 곧 에이전트 런타임의 뼈대** |
| 06 | xv6 swtch.S, scheduler() 분석 | MLFQ 스케줄러 설계 |

마지막 행이 핵심이에요. **Week 6에 만든 유저레벨 스레드 라이브러리가 에이전트 런타임의 절반입니다.** *"우리는 0부터 시작하는 게 아니라, 과제로 만든 걸 확장해서 시작한다"* — 이 한 줄이 발표 슬라이드 첫 페이지가 될 수 있어요.

B를 선택하면 이 자산들이 그대로 잠듭니다. 학기 마지막에 *"우리가 이번 학기에 뭘 배웠지?"* 질문에 답할 게 줄어요.

## 4. 앞으로 배울 게 우리 다음 모듈입니다

이건 진짜 신기한 매칭이에요:

```
강의 진도                         프로젝트 빌드 순서
─────────────                    ─────────────────
Week 09 sleep/wakeup        →    에이전트 메시지 큐 (blocking)
Week 10 데드락               →    리소스 쿼터 데드락 회피 설계
Week 11 paging               →    컨텍스트 윈도우 = 가상 주소 공간
Week 12 LRU/Clock 페이지 교체 →   KV-cache / 메시지 eviction
Week 13 FS allocation        →    샌드박스 파일시스템 격리
```

특히 **Week 12 — 페이지 교체 알고리즘** 이 우리 프로토타입 통합 시기와 맞물립니다. 그 주에 배운 LRU/Clock을 *그 주에 코드로 옮기면* 됩니다. 이런 정렬은 우연이 아니에요.

## 5. "그래도 망할까봐 무섭다"에 대한 답

B 팀들이 무서워하는 그 시나리오 — *"6주 후에 데모할 게 없다"* — 우리는 **모듈 분리 설계**로 막을 수 있습니다:

- **각 모듈을 독립 데모 가능하게** — 스케줄러 단독 시연 (큐에 5개 에이전트 → 라운드로빈 시각화), 메모리 관리자 단독 시연 (eviction 동작), 샌드박스 단독 시연 (격리 violation 차단). **한 모듈이 망가져도 발표 자료가 비지 않음.**
- **Week 11까지 무조건 end-to-end 뼈대 완성** — 스케줄러 1종(RR)만, 메모리 1종(LRU)만, 도구 1개만. 일단 *"에이전트 2개가 동시에 파일 하나 읽는다"* 만 되면 그 다음은 살 붙이기.
- **폴백 영상 미리 녹화** — Week 13 dry-run 전에 라이브 시연 백업용 GIF 확보.

이러면 A의 천장은 가져가면서 B의 안전감까지 같이 챙깁니다.

## 6. 구체적 청사진 — Solar-Agent OS

> "여러 LLM 에이전트를 동시에 안전하게 굴리는 미니 사용자공간 OS"

**핵심 모듈 7개:**
1. Process model — 에이전트 = PCB-like 구조체, 상태 전이 (Week 2 활용)
2. Scheduler — MLFQ로 토큰 단위 시간 분할 (Week 6-7 활용)
3. Worker pool — Solar API 호출 워커 스레드 풀 (Week 5 그대로)
4. Synchronization — 락/세마포어로 공유 자원 보호 (Week 4, 9, 10)
5. IPC — 에이전트 간 메시지 큐 (Week 2 pipe + Week 9 sleep/wakeup)
6. Memory manager — 컨텍스트 윈도우 LRU eviction (Week 11-12)
7. Sandbox FS — 도구 호출 시 격리 (Week 13)

**평가 지표 (Week 12 전까지 결정):**
- 동시 에이전트 수에 따른 throughput / fairness
- eviction 정책별 응답 정확도 vs 메모리 절감률
- 샌드박스 violation 차단율

## 7. 역할 분담 제안 (4명 기준)

- **A (런타임/스케줄러)** — 프로세스 모델 + MLFQ 스케줄러. Week 6 과제 확장이 출발점.
- **B (메모리)** — 컨텍스트 가상화 + LRU/Clock eviction. Week 11-12 진도가 곧 작업.
- **C (샌드박스/도구)** — 도구 호출 격리 레이어 + FS 권한 모델. Week 13 진도와 동행.
- **D (IPC + 대시보드 + 평가)** — 메시지 큐 + 모니터링 UI(프로세스 테이블 시각화) + 측정 지표.

각 사람이 **본인 모듈 단독 데모**를 책임지면, 한 명이 막혀도 전체가 무너지지 않습니다.

## 8. 차별화 포인트 — 발표에서 우리가 받을 한 마디

다른 팀이 다 *"LLM으로 OS를 도와주는 도구를 만들었습니다"* 라고 발표할 때, 우리는:

> *"저희는 LLM 에이전트를 OS의 워크로드로 보고, 그 위에 동작하는 미니 사용자공간 OS를 직접 설계·구현했습니다. 강의에서 배운 7개 OS 개념이 이 시스템의 7개 모듈에 정확히 대응됩니다."*

이 한 단락은 교수 평가(15%) + Peer review(15%) 모두에서 강력하게 작동해요. *"OS 개념을 어디서 어떻게 썼는가"* 질문에 페이지 한 장으로 답이 됩니다.
